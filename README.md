# 数据驱动实体框架（Unity）

> 一个以"配置即实体、实体自管理、通道只路由"为核心的 Unity 游戏框架。
> 七个系统窄接口协作，无全局上帝表，加配置/实体/事件都是"零注册"或"加一条"。

---

## 这是什么

一套面向 **数据驱动 + 实体组件化** 的 Unity 框架，解决三个问题：

- **实体怎么造**：蓝图声明"要什么"，8 步工厂流水线按固定流程挂组件
- **实体怎么活**：四层结构（Root/Logic/View/Audio）+ 四维状态（生死/流程/动作/Buff）
- **实体怎么通信**：输入发布标准化语义，事件按 UUID 精准投递，实体自己解释

适用场景：中小型 Unity 项目、需要大量配置化实体的游戏（策略/塔防/Roguelike/模拟经营）。

---

## 核心价值

### 1. 没有全局上帝表

实体不查全局表。通道把信息送到实体面前，实体被选中/被注册/被投递时才响应。

- **入口注册**：只有注册过的实体收事件（`EventManager._uuidIndex`）
- **方法注册**：只有注册过的方法被执行（`EventEntryBase._table`）
- **三不**：不查全局表、不广播过滤、不全量 switch

> 详见《架构优点》A1~A4

### 2. 配置即实体，零注册

加一个配置类 = `[Config]` + 写 JSON，不改任何管理代码。
加一种实体 = 加一条蓝图配置，现有工厂够用则零代码。

- 元配置驱动：`[Config(configId, priority, dependsOn)]` 自动发现、校验、排序
- 蓝图组装：共性在基类，特质在子类，工厂流水线按配置挂组件
- 事件代码生成：编辑器配 + 一键生成 + 编译即用

> 详见《架构优点》B1/B2/B5

### 3. 双轨输入：状态机 + 权威快照

同一按键在不同情境映射不同功能，五层解耦（上下文/模式/状态机/拦截器/意图）。

- **持续状态**（移动/瞄准）用权威快照轮询 `IsActionHeld`，不丢帧、不残留
- **瞬时机**（攻击/交互）用事件投递 `InputOutputPayload`，可拦截、可 CD
- 组合优先 + 单键兜底 + 50ms 释放缓冲

> 详见《架构优点》B4

### 4. 实体自管理：Root 容器就是实体自己的全局表

实体不知道自己的预制体有什么部位，但它的逻辑脚本可以定义配置，配置通过逻辑状态系统注册进来。
需要知道自己受击音效时，直接去 `Entity.Root` 找。

- 怪物受击例子：射线检测到"弱点" → 事件投递 → 怪物查自己定义的"部位→倍率"表 → 加倍受伤
- 逻辑脚本是"实体对自身信息的解释器"，配置是"实体对自身信息的定义"

> 详见第 3 章 3.1、第 7 章 7.5

## 关键设计决策

| 问题                   | 方案                                       | 收益                                |
| ---------------------- | ------------------------------------------ | ----------------------------------- |
| 实体怎么知道全局有什么 | **不查全局表**，通道送到实体面前           | 无全局锁/无全局遍历，实体可独立测试 |
| 事件怎么精准投递       | **入口注册 + 方法注册**                    | 未注册实体/方法零开销               |
| 配置怎么自管理         | **元配置**（`[Config]` 描述配置）          | 加配置零注册，自动排序/校验依赖     |
| 实体怎么组装           | **蓝图声明 + 工厂流水线**                  | 加实体从写函数变成写配置            |
| 输入怎么分情境         | **五层解耦**（上下文/模式/状态/拦截/意图） | 改配置即改行为                      |
| 实体怎么自解释         | **逻辑脚本定义配置 + 状态系统注入**        | 预制体换了部位名，改配置即可        |

## 快速开始

### 环境

- Unity 2021.3+（URP 或 Built-in 均可）
- Newtonsoft.Json（事件系统用，Package Manager 装）

### 启动流程

1. 场景挂 `GameManager`
2. 场景预挂摄像机（Tag: `Camera_Main`）和画布（Tag: `Canvas_Main`）
3. 运行，`GameManager.Awake` 按顺序创建 9 个系统
4. `Start` 延迟 0.5 秒后 `InitGame`（批量生产 + 加载状态）

### 从哪读起

- **新人**：第 0 章总览 → 《架构优点》A1~A4 → 第 6 章总控

- **加按键/状态/拦截器/意图**：第 4 章 4.6
- **加事件**：第 5 章 5.6

## 已知限制（诚实标注）

- **P0 阻塞级**：事件配置打包后读取失效（ISSUE-P0-001）；输入 Area 范围模型 ID 命名不一致（ISSUE-P0-002）
- **P1 重要级**：`ForbidAll` 下移动未拦（ISSUE-P1-001）；脚本挂载隐性依赖（ISSUE-P1-002）；移动 + Rigidbody 抖动（ISSUE-P1-006）；退出保存顺序不保证（ISSUE-P1-007）
- **未完成**：地图编辑器、改键完整化、CanListen 接入、异步加载器

> 完整台账见《已知问题与待修点》。

## 设计起点（背景锚点）

本项目起源于独立开发者的四次认知迭代：

1. **事件机制** → 理解信息通信的解耦
2. **元配置思想** → 理解数据驱动数据、系统自管理
3. **蓝图组件式加载** → 理解共性/特质分离
4. **输入系统的"语义与信息"** → 理解"事件是显式信息，意义是加密信息；解释权应交给实体"

架构的每个结构决策都能追溯到这四个节点。完整心得见《开发历程 / 个人心得》。
